# Fail-closed Meta publisher service for Facebook and Instagram Reels

This module ports the audited Facebook Page Reels and Instagram Professional/Reels flows behind the shared publisher contract and the provider-operation repository. Graph calls use configured versioned URLs and authorization headers, while the service keeps writes disabled by default and exposes only internal publish/reconcile routes. The mock HTTP tests cover the main Facebook phases, the Instagram container flow, HTTPS storage, redaction, and read-only reconciliation, but they do not establish the complete service wiring or several final safety boundaries. **Watch for:** **critical/confirmed** capability-blind idempotency replay; **important/confirmed** provider/account admission and write-gate gaps; **important/confirmed** unused request/upload deadlines; **important/confirmed** Facebook remote-session creation before local-asset validation; **important/confirmed** credential-bearing media URLs being forwarded; and **minor/confirmed** reconciliation and application-context test gaps.

**Verdict**: NEEDS_CHANGES

## High-level view

The provider wire topology matches the brief: Graph calls use Bearer, Facebook rupload uses OAuth, service-generated access tokens stay out of URLs/forms, and both phase sequences preserve the audited identities, status polling, retry boundaries, caption handling, storage, and permalink behavior.

The service uses only `ProviderOperationRepository` for idempotency, but its fingerprint omits capability. A command key can therefore replay a completed Facebook result as an Instagram operation. The internal guard also stops short of provider credentials and configured account binding, while its advertised request/upload deadlines are not applied to the HTTP client.

Two provider-boundary gaps remain: Facebook starts a remote session before validating a local asset, and accepted HTTPS media URLs may carry credential-shaped query/userinfo into provider form fields. Reconciliation stays read-only, but malformed reconciliation input is not validated and can be returned as HTTP 200 with a reconciliation lifecycle result.

The support auto-configuration provides the repository/entity/Flyway topology and writes default to disabled, but no Meta application-context test proves that wiring. The migration-readiness document still records no live Graph, deployment, or shared-database evidence; this local review does not attempt to close those external gates.

<summary>Issues (7)</summary>

1. **Critical — Capability-blind idempotency** — **confirmed:** the operation fingerprint excludes the capability, so the same key can replay a Facebook result for Instagram or the reverse. Include capability in the claim identity and add a cross-capability replay test.
2. **Important — Provider/account admission** — **confirmed:** the publish guard does not require provider credentials and configured Page/Instagram IDs are unused. Enforce credential presence and target-account binding before claiming or calling a provider, or explicitly remove those configuration promises.
3. **Important — Unbounded provider I/O** — **confirmed:** request/upload timeout properties are never applied to `RestClient`. Configure bounded graph/upload request factories and test the deadline behavior.
4. **Important — Facebook asset preflight** — **confirmed:** a missing local asset is discovered only after Facebook creates an upload session. Validate local files before the start POST and reserve reconciliation for post-submission uncertainty.
5. **Important — Credential-bearing media URLs** — **confirmed:** HTTPS validation accepts query/userinfo and forwards the value as `file_url`/`video_url`. Reject sensitive URL credentials while retaining approved non-secret signed parameters.
6. **Important — Reconciliation request/status boundary** — **confirmed:** the reconcile body lacks validation for declared fields and malformed/provider failures collapse into HTTP 200 reconciliation results. Validate input and distinguish bad requests from uncertain provider reads.
7. **Minor — Runtime and negative-path evidence** — **confirmed:** tests do not boot the Meta application or cover the blocker paths, several Instagram error states, URL credentials, or cleanup failures. Add a mocked service-context test and targeted regressions.

### Provider wire contract and phase semantics

`MetaClientSupport` centralizes form encoding, response parsing, retry decisions, and redaction. **Confirmed:** `postForm` and Graph `get` use `Bearer` headers, `postUpload` uses the audited `OAuth` header, and the helper never appends the configured provider token to the request URI or form map (`MetaClientSupport.java:64-116`). The Facebook client performs start, rupload transfer, status polling, finish, and best-effort permalink lookup; the Instagram client performs `media`, status polling, `media_publish`, and best-effort `permalink` lookup. Their normalized identities match the contract: Facebook uses `post_id` with the video ID fallback, while Instagram returns the published media ID as `providerPostId`.

**Confirmed:** retry phases are wired through the shared `RetryPolicy`: start/container calls may retry before submission, upload/finish or media-publish failures after submission become reconciliation-required when uncertain, and polling remains read-only. Facebook maps uploading/processing errors and timeout separately; Instagram maps `ERROR`/`EXPIRED` to terminal provider rejection and timeout to reconciliation. The local tests provide useful evidence for these main sequences, including Facebook auth/rate-limit/server failures and both platform timeouts.

### Capability-blind idempotency replay

**Critical/confirmed:** `MetaPublishService.publish` normalizes the capability and then calls `operationRepository.claim(normalizedCommand)`, but `ProviderOperationRepository` fingerprints only `PublishCommand`; `PublisherCommandFingerprint` has no capability input. The same idempotency key and command can therefore be claimed under `facebook_reels`, completed, and later replayed under `instagram_reels` as the stored Facebook result without invoking either provider client. The reverse direction has the same problem. This violates the capability-selected API contract even though there is no second queue or ledger.

The fix must bind capability to the persisted operation identity, either by including it in the fingerprint/claim contract or by storing and comparing it as part of the provider-operation record. Add a cross-capability replay/conflict test and keep the existing same-capability completed/in-flight tests.

### Provider credentials and target-account admission

**Important/confirmed:** `MetaWriteCapabilityGuard.assertPublishAllowed` checks only the internal token, `writeEnabled`, `publishEnabled`, caller header, and capability syntax (`MetaWriteCapabilityGuard.java:42-52`). It has no provider-credential gate, despite the Task 3 architecture requiring credentials as a publish admission condition. With valid internal headers and enabled flags, a missing provider token reaches the client and returns a normalized `FAILED` result from a nominally successful HTTP request rather than being rejected by the write boundary.

**Important/confirmed:** `MetaPublisherProperties.facebookPageId` and `instagramAccountId` are bound but never used for admission or edge construction. Both clients use `command.platformAccountId()` directly (`FacebookReelsClient.java:58-64`; `InstagramReelsClient.java:62-79,98-101`). If a configured token can access more than one Page/account, an authenticated caller can direct that token at an unbound target. Require nonblank credentials and bind the command target to the configured account, or remove the unused account configuration and explicitly make caller-owned target identity part of the security contract. Cover missing-credential, mismatched-account, and enabled-flag responses at the controller boundary.

### Provider I/O is not bounded by the configured deadlines

**Important/confirmed:** `application.yml` exposes `request-timeout` and `upload-timeout`, and `MetaPublisherProperties` binds them, but neither property is read by `MetaClientSupport` or either client. The helper constructs `RestClient` with `builder.build()` and every request method has no timeout argument (`MetaClientSupport.java:40-61,64-116`). Poll deadlines only run after a status response arrives; a blocked connect/read/upload can exceed the advertised 120-second or 600-second limits indefinitely. Configure the underlying request factory/client with the graph and upload deadlines (or pass bounded request options) and add a deterministic timeout test.

### Facebook creates a provider session before validating local assets

**Important/confirmed:** `FacebookReelsClient.publish` sends the start POST before `upload` checks `Files.exists`/`Files.isRegularFile` (`FacebookReelsClient.java:63-84,175-193`). A missing local path consequently creates a remote video session, then returns `RECONCILIATION_REQUIRED` through the generic runtime-error path. The audited Python implementation checks the local path before the start request. This produces avoidable provider-side orphan state and classifies a caller input error as uncertain provider state. Validate local assets before the start POST; retain reconciliation handling for failures that occur after a real provider submission.

### HTTPS media URLs can carry credentials through the provider form

**Important/confirmed:** the service itself correctly avoids adding Meta tokens to URLs, but `ConfiguredPublicMediaStorage.isHttps` accepts any HTTPS URI with a host, including userinfo and query parameters (`ConfiguredPublicMediaStorage.java:28-35,103-110`). The accepted value is then sent as Facebook `file_url` or Instagram `video_url`. A command containing `?access_token=...`, another sensitive token query key, or URI userinfo is therefore forwarded to Meta in a form field, contrary to the no-token-in-URL/form constraint. Reject credential-bearing query keys and userinfo at the shared command/storage boundary while preserving explicitly supported non-secret signed URL parameters, and add a regression test.

### Reconciliation input and HTTP status handling

**Important/confirmed:** `POST /internal/v1/reconcile` checks the internal token and capability syntax but does not apply `@Valid` or validate `publicationAttemptId`, `platformAccountId`, or the relationship between the supplied account and provider identity (`MetaPublisherController.java:42-53`; `MetaPublishService.java:102-138`). The service only requires one provider ID, ignores the account argument inside both clients, and converts any client/runtime failure into a `RECONCILIATION_REQUIRED` result. Consequently, malformed reconciliation requests can return HTTP 200 with a lifecycle result instead of HTTP 400, and the declared reconciliation fields do not form an enforceable contract. Add explicit request validation and distinguish invalid input from a provider lookup that genuinely needs reconciliation. Keep provider lookup strictly GET-only.

The publish controller’s explicit 401/403/409/400 handlers are aligned with the brief, and uncertain provider outcomes are represented through the shared result lifecycle rather than a second delivery mechanism. The missing negative-path assertions mean those mappings are not yet fully demonstrated.

### Test scope and runtime wiring evidence

**Minor/confirmed:** the service tests cover successful Facebook and Instagram mock sequences, Facebook auth/rate-limit/5xx handling, HTTPS/local storage cases, caption truncation, timeout results, duplicate/in-flight service behavior, and a read-only reconcile mock. They do not cover capability-crossed idempotency, provider credential/account gates, configured HTTP/upload deadlines, missing-local-file preflight, credential-bearing asset URLs, Instagram `EXPIRED` and 401/429/5xx cases, cleanup on provider failure, publish 409 handling, malformed reconciliation bodies, or the default-disabled property combination.

**Minor/confirmed:** no test boots `MetaPublisherApplication` with its actual `RestClient.Builder`, `MetaPublisherProperties`, support auto-configuration, JPA entity scan, repository, and isolated Flyway migration. The support module has consumer-shaped tests, but they do not prove this concrete Meta application starts with its own package root and configuration. Add one service-context test with a stub datasource or test profile and keep all provider calls mocked. No live provider or network test is required for this review; the migration-readiness document explicitly records that live Graph, deployment, and shared-database evidence is absent.

# Pre-render evidence separation and render-stage gating for Luca Sticky Ball

The working-tree changes tighten prompt parsing around labelled attempts, preserve leading-verb inference as audit-only evidence, and expose canonical active-attempt and strategy-family data to the quality projections. They also add explicit goal/mechanic evidence, escalation evidence, first-frame staging, nullable score plumbing, and render-queue checks. The focused Luca/second-pass Python tests pass, and the render-service policy tests pass. **Watch for:** **confirmed** final-video authorization can still report `AUTHORIZED` without requiring `RENDER_READY` or independent evidence; **confirmed** a partially applicable family can still expose a numeric score while its status says `PARTIAL`.

**Verdict**: NEEDS_CHANGES

## High-level view

The parser/evidence path now distinguishes author-declared attempts from leading-verb candidates. The Luca golden path reports two active attempts, keeps the `GRABS` escalation beat out of the active count, and derives escalation from the changed target.

The assessment separates textual first-frame eligibility from pending visual evidence, and the render queue treats `FIRST_FRAME` differently from `VIDEO`: first-frame requests use prompt-stage eligibility, while video requests require `RENDER_READY` and independent revalidation. The assessment projection itself does not enforce the latter contract, so it can disagree with the queue boundary.

Nullable score handling is correct for families with no evaluable result and regression arithmetic skips `None`. The mixed-family path is not fully consistent: `NOT_APPLICABLE` alongside an evaluated result produces a numeric score but a `PARTIAL` status.

<summary>Details</summary>

### Final video authorization versus prompt-stage eligibility

`intelligence/ml-service/app/assessment/pre_render_assessment.py:427-478` decides `AUTHORIZED` from service errors, non-evidence creative failures, and pending first-frame/silhouette evidence. It never checks the report's readiness status, blocker/critical counts as a final predicate, or the existence of independent revalidation. A direct probe with a `NEEDS_REVISION` report at score 85 and both visual checks marked `AVAILABLE` returns `{"status": "AUTHORIZED", "final_video_render": "AUTHORIZED"}`. That is a false authorization for the contract described by the new fields.

The downstream queue is safer: `intelligence/creative-render-service/src/main/java/com/pompom/creative/queue/ValidationEvidencePolicy.java:21-57` still requires `RENDER_READY`, and for non-first-frame jobs requires independent revalidation. This prevents the current queue from rendering, but leaves the assessment/UI and any caller consuming `final_video_render` with a weaker policy than the actual gate. The assessment should keep `READY_FOR_FIRST_FRAME` independent from a final-video authorization that remains pending until authoritative `RENDER_READY` plus independent evidence is available.

### Nullable family scores and partial coverage

`intelligence/ml-service/app/rules/rule_engine.py:333-351` excludes `NOT_APPLICABLE` from the numerator/denominator, but only an `UNKNOWN` companion forces the family score to `None`. For one `PASS` and one `NOT_APPLICABLE` in the same family, the result is `100.0` while `_calculate_family_assessments` reports `status: PARTIAL` and `evidenceCoverage: 50`. The new comment immediately above the assignment says any unknown/not-applicable companion should keep the score out of the projection, so the implementation and its own contract disagree. The score should be nullable for partial coverage (and the same policy should be applied consistently to service-error companions), or the status/contract must explicitly say that the numeric value is only an evaluated-subset score.

### Coverage still missing at the boundaries

`intelligence/ml-service/tests/test_prompt_quality_second_pass.py:121-155` verifies the assessment's textual first-frame result and constructs an evidence-gap rule directly. `intelligence/creative-render-service/src/test/java/com/pompom/creative/queue/ValidationEvidencePolicyTest.java:260-318` verifies the queue policy using a manually supplied boolean; those tests do not exercise `ValidationEvidenceService.isFirstFrameEligible` reading the stored report snapshot (`intelligence/backend/src/main/java/com/pompomhills/intelligence/quality/ValidationEvidenceService.java:72-81`), so a persisted-key/schema mismatch could pass the current tests. The Luca golden tests validate mechanic/goal/fake-resolution representation, but do not invoke `PAYOFF_003` against the parsed Luca IR; its existing tests use synthetic IR and mocked semantic results. Add tests for these actual boundaries rather than only unit-level projections.

# Provider-neutral publisher support and operation idempotency

Task 2 adds a provider-neutral Maven support module with shared command validation, error/retry decisions, secret redaction, durable provider-operation mapping, and a Flyway migration. The entity/table deliberately carries provider-operation state without control-plane foreign keys, and the focused reactor build passes all 22 support tests plus packaging. **Critical (confirmed):** the concurrent claim recovery path cannot query PostgreSQL after its uniqueness violation aborts the transaction. **Critical (confirmed):** the redactor leaks credentials for non-Bearer authorization formats and other credential-shaped content. **Important (likely/confirmed):** planned publisher services will not discover the shared repository/entity without extra wiring, reused idempotency keys are not bound to request identity, and unrelated Family 6 changes are bundled in the working tree.

Watch for: **critical/confirmed** concurrent claims failing instead of returning one existing operation; **critical/confirmed** `Authorization: Basic`/`Token` and credential-shaped values surviving redaction; **important/likely** missing Spring entity/repository discovery in the planned service package roots; **important/confirmed** a reused key returning a result for a different command; **important/confirmed** unrelated ML/Family 6 behavior changes in a Task 2 diff; and **minor/confirmed** schema lengths that are not enforced by the request/result boundary.

**Verdict**: NEEDS_CHANGES

## High-level view

The shared module has no provider client, endpoint, remote call, queue, or render-control-plane repository dependency. Its entity and migration store the requested provider-operation fields and intentionally avoid foreign keys into `publication_jobs` or `publication_attempts`, but **likely** production consumers will miss the support entity/repository because the only Spring test supplies scanning and import configuration manually.

The sequential idempotency case works with a unique command key and persisted result, yet the first-claim race is **confirmed** to be unrecoverable transactionally on PostgreSQL. The key is also treated as the entire request identity, so a different command carrying an already-used key is silently mapped to the prior operation.

The redactor removes known secrets, Bearer values, and several assignment forms, but **confirmed** authorization matching redacts only the scheme for unquoted non-Bearer headers. Credential-shaped suffixes and bare token forms can therefore reach the normalized message field.

The working tree also contains Family 6 canonical-evidence and golden-comparator changes unrelated to the publisher-support brief; this scope contamination is **confirmed** and changes semantic status and baseline gating.

<summary>Details</summary>

### Concurrent claims do not recover on PostgreSQL

The concurrent path is **confirmed** to be unsafe: two transactions can both observe no row, the loser blocks on the unique constraint, and `entityManager.flush()` raises `PersistenceException`. The catch block calls `clear()` and immediately issues another JPQL query in the same transaction. PostgreSQL marks that transaction aborted after the constraint violation, so the query cannot recover the winner; Spring can also reject the method at commit because the transaction is rollback-only. The unique constraint prevents two committed rows, but this method does not reliably return `OperationClaim(false, existing)` to the losing caller, which leaves the caller without a safe, uniform idempotency decision before remote work.

`ProviderOperationRepositoryTest` covers two sequential claims and an in-flight row on H2, but it has no concurrent execution and no PostgreSQL database. Replace exception-driven recovery with a conflict-safe insert (`ON CONFLICT DO NOTHING` with a follow-up read) or isolate the failed insert and lookup in separate transactions. Add a Testcontainers PostgreSQL test that races two claims and asserts exactly one `newOperation()` result, a stable existing operation for the other caller, and no second provider invocation.

### Authorization redaction leaves credential-shaped content

`SecretRedactor` first handles Bearer values, then its authorization-assignment pattern treats the first whitespace-delimited token as the value. For `Authorization: Basic dXNlcjpwYXNz`, the observed output is `Authorization: [REDACTED] dXNlcjpwYXNz`; `Authorization: Token abc123` behaves the same way. This is **confirmed** by exercising the compiled class, and the remaining suffix is exactly the credential-shaped content the shared policy must prevent from reaching logs or the persisted `message` field.

The bypass is broader than authorization headers: a bare JWT/opaque token after the word `token` is not an assignment and is left unchanged, while `redactFields` does not classify `accessKey` as sensitive. The module has no raw-response column, but provider-controlled message text is still persisted after this incomplete sanitization. Parse or structure provider responses before logging, redact the full value of every authorization scheme up to a safe delimiter, expand sensitive key detection to credential aliases, and pass known credential values whenever the caller has them. Tests need Basic, Token, Digest-style, quoted/JSON, query-string, bare JWT, and map-key cases—not only Bearer and `access_token=`.

### Shared JPA state is not self-wired into planned publisher services

The table/entity shape is intentionally isolated from the control plane: it records job/attempt identifiers as values, adds no foreign keys, and has converters for the contract wire values. The deployability gap is **likely** in Spring discovery. The only application configuration in the module test explicitly uses `@EntityScan(basePackageClasses = ProviderOperationRecord.class)` and `@Import(ProviderOperationRepository.class)`. The planned applications are rooted at `com.pompom.metapublisher`, `com.pompom.tiktokpublisher`, and `com.pompom.youtubepublisher`; default component/entity scanning from those roots will not include sibling package `com.pompom.publishersupport`, and the module supplies no auto-configuration imports.

Add a support auto-configuration that registers the repository and entity package, or require each consumer to import and scan the support package explicitly. Exercise the actual consumer topology, Flyway migration, Hibernate `validate`, and PostgreSQL connection in an integration test; the current H2-only module test does not establish that a publisher service can boot with this library.

### Idempotency keys do not identify the command payload

`ProviderOperationRecord` persists `publicationJobId`, `publicationAttemptId`, and `commandIdempotencyKey`, but not the immutable asset reference/hash, platform account, or normalized publication options. `claim` returns the existing row as soon as the key matches, before comparing the incoming command with the original. This behavior is **confirmed** in the code and means a reused key can suppress a new provider operation while returning provider IDs and a result belonging to a different asset, account, or attempt.

Persist a hash of a canonical, non-secret command projection and reject a key reuse whose fingerprint differs. If keys are intentionally scoped by account/provider rather than globally unique, include that scope in the stored identity and database constraint; do not silently alias different commands.

### Task 2 is mixed with Family 6 semantic changes

The working-tree diff also changes `ml-service/app/quality/canonical_evidence.py`, `ml-service/app/golden/comparator.py`, and their Family 6 tests. Those additions change missing-evidence classification and baseline-gating behavior, so they are not harmless formatting or shared-build changes. This scope violation is **confirmed** against the Task 2 brief and its constraint to keep unrelated work out of the migration.

Remove the ML files from this change or split them into a separate review with its own behavioral evidence. Keep only the publisher-support module and the reactor registration here.

### Entity column limits and validator limits disagree

`command_idempotency_key`, `provider_request_id`, `provider_post_id`, and `provider_video_id` are `VARCHAR(200)` in the migration and have matching JPA lengths. The shared validator only applies `@NotBlank` through `PublishCommand`; it has no maximum for the command key, and `PublishResult` has no maximum for provider IDs. This mismatch is **confirmed** and turns an oversized internal command or provider response into a persistence exception rather than a fail-closed boundary error.

Add explicit maximum-size validation before claim/result persistence, or deliberately use `TEXT` and document the larger contract. Add boundary tests for each persisted string rather than relying on Hibernate/database failure.

### OAuth discovery still exposes the user token in URLs

**High — confirmed:** `MetaOAuthService.java:181-215` sends the exchanged user token through `.queryParam("access_token", userAccessToken)` for both `/me/accounts` and the selected Page details call. The corresponding fixtures at `MetaOAuthServiceTest.java:56-65,113-121` require the secret in the URI, so the regression is protected by the tests rather than detected. URL query strings can be retained by HTTP infrastructure and logs; send the user token through the bearer header, and leave query parameters only where the provider contract truly requires non-token OAuth exchange values.

### Linked Instagram discovery lacks Professional-account evidence

**Important — confirmed:** `MetaGraphReadClient.java:26-28,494` models the nested linked account as an ID only, while `MetaAccountDiscoveryService.java:147-160,274-283` passes `null` for `instagramAccountType` and persists `instagramAccountEligible=false`. The capability gate consequently returns `UNKNOWN` for every Instagram capability at `MetaAccountDiscoveryService.java:309-311`, and the response hard-codes `mediaEligibility=UNKNOWN` at lines 247-252. `MetaAccountDiscoveryServiceTest.java:66-69` asserts this incomplete result. Request the linked account’s provider type/eligibility (the existing account DTO’s type field is not requested), persist the validated type and eligibility, and test eligible Business/Creator, missing-link, and ineligible responses.

### Page target eligibility is disconnected from provider evidence

**Important — confirmed:** `MetaAccountDiscoveryService.java:255-262` constructs every `PageTarget` with `pageEligibility=SUPPORTED`, while the capability calculation at lines 274-281 can see `accessTokenAvailable=false` and can return `UNKNOWN` or `MISSING_PERMISSION`. A Page returned by `/me/accounts` without an access token can therefore be presented as eligible even though the service cannot use it. Derive Page eligibility from the relevant capability/token evidence and add a fixture for an omitted Page token and missing Facebook scope.

### Discovery routes do not establish a caller boundary

**Important — likely:** `MetaConnectionController.java:39-48` exposes GET and POST discovery without an authorization annotation or caller identity, and `MetaAccountDiscoveryService.java:473-475` scopes lookup to the process-wide `connectionOwnerKey`. The GET handler calls the transactional discovery method, which performs a provider request and updates durable state, so an untrusted caller could enumerate account metadata, trigger repeated provider calls, or select arbitrary IDs within the shared owner namespace. Derive the owner from the authenticated principal and authorize the requested connection; make GET a cached/read-only projection or explicitly protect and rate-limit the discovery action.

### Passing tests do not cover the failing contract edges

**Important — confirmed:** the focused command passes 20 tests, but `MetaAccountDiscoveryServiceTest.java:101-124` exercises only a two-page de-duplication scenario rather than the four-request/100-target cap, and no test supplies an Instagram account type or an ineligible Page. `MetaOAuthControllerTest.java:156-205` checks successful route delegation and secret omission but not owner isolation, missing connections, or provider failures. Add those cases and change the OAuth fixtures to assert bearer headers and token-free URIs.

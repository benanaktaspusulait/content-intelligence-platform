# Fail-closed Meta publisher admission and capability-scoped publication state

Task 3 hardens the Java Meta publisher around Facebook Page Reels and Instagram Professional Reels: provider/account credentials are admitted before the idempotency claim, operation state is capability-scoped with a V2 backfill, media hosting is explicit HTTPS-only, and Graph/rupload calls have bounded deadlines. Facebook and Instagram preserve uncertain outcomes and require publication evidence before claiming completion; the focused Meta suite (50 tests) and contract/support suite (39 tests) pass. The same patch also changes validation-evidence DTOs and render admission in the backend and creative-render-service, which is unrelated to the Meta publisher scope. **Watch for:** **important/confirmed** scope contamination; **important/confirmed** emoji captions rejected before claim; **important/confirmed** reconciliation completion based on echoed rather than returned IDs; and **important/confirmed** provider upload URLs receiving OAuth without URL validation.

**Verdict**: NEEDS_CHANGES

## High-level view

The publish path now validates and admits the configured capability, target account, and provider credential before creating a capability-bound operation claim. The support migration preserves legacy rows by mapping the existing `facebook_reels:` and `instagram_reels:` key prefixes, while legacy repository overloads remain available. **Minor/confirmed:** that compatibility behavior is not exercised against a populated pre-V2 schema.

The provider topology is bounded and fail-closed: Facebook validates local assets before its start request, Instagram requires a caller HTTPS URL or explicit storage backend, Graph and rupload requests use configured deadlines, and completion is not inferred from a missing Facebook publication proof. **Important/confirmed:** the Facebook upload URL returned by the start response bypasses the same HTTPS, credential, and path checks applied to configured endpoints.

Reconciliation performs provider reads only and checks for an evidence-bearing response, but both clients preserve caller-supplied IDs in the completed result and the service accepts a match across either ID field. **Important/confirmed:** a response whose returned object ID differs from the requested object can therefore be recorded as completed, defeating the conservative evidence gate.

**Important/confirmed:** the Instagram helper truncates by Unicode code point, but the service-level path still runs the result through a shared UTF-16 `String.length()` caption bound, so valid emoji-heavy captions can be rejected before claim. **Important/confirmed:** the backend/render evidence changes add a separate Family 8 authorization gate outside this publisher task, and **minor/confirmed** tests omit the service-level Unicode case, returned upload URL rejection, reconciliation identity mismatch, cleanup on provider failure, and executable V1-to-V2 migration compatibility.

### Admission-before-claim and capability-scoped migration

The ordering in `MetaPublishService.publish` is aligned with the write boundary: capability normalization and command validation occur at `MetaPublishService.java:53-57`, configured account/credential admission occurs at `:58-59`, and only then does `ProviderOperationRepository.claim` run at `:64-66`. The controller applies the same provider binding before delegation, and the direct-service negative test verifies that missing credentials produce no repository or provider interaction. This closes the earlier admission-before-claim risk without introducing a second queue or ledger.

`ProviderOperationRepository` now scopes lookup, insert, result recording, and reconciliation lookup by `PublisherCapability`; the native PostgreSQL insert uses the matching composite conflict target. `V2__scope_provider_operations_by_capability.sql` backfills old Meta-bound keys from their capability prefixes before replacing the unscoped unique constraint, and the legacy overloads continue to use the `legacy` marker. **Minor/confirmed:** `ProviderOperationRecordMappingTest` and the repository tests inspect the migration text and exercise the post-migration mapping, but no test starts with a populated V1 table, runs V2, and verifies that old Meta rows replay while arbitrary legacy rows remain legacy. Add an executable migration fixture covering those rows and the new same-key/different-capability uniqueness before relying on this compatibility claim.

### Reconciliation evidence is not bound to the returned provider identity

**Important/confirmed:** both reconciliation clients verify that the response contains an ID and publication evidence, but then return the requested IDs when they were supplied instead of the ID read from Meta. Facebook does this at `FacebookReelsClient.java:207-211`; Instagram does it at `InstagramReelsClient.java:190-194`. `MetaPublishService.matchesRequestedIdentity` then accepts any cross-field equality at `MetaPublishService.java:196-200`. For example, a Facebook lookup requested with `providerVideoId=video-requested` can receive `{id:"different-video", permalink:...}` and still return `providerVideoId=video-requested`; the service sees its own echoed value and persists `COMPLETED`.

The client should require the returned `id` to equal the exact identity used in the GET (and preserve provider-post versus provider-video namespaces), then return the actual evidence IDs. The service should compare those actual IDs to the persisted operation/requested identity without cross-matching post and video fields. Add mismatch tests for both clients and a service test proving that a mismatched response remains `RECONCILIATION_REQUIRED`.

### Code-point truncation stops at the shared UTF-16 validation boundary

**Important/confirmed:** `MetaPublishService.normalizeCommand` correctly measures the incoming Instagram caption with `codePointCount` at `MetaPublishService.java:211-225`, and `InstagramReelsClient.truncateCaption` keeps the ellipsis within 2200 code points. However, a caption containing 2200 emoji code points has 4400 UTF-16 code units, so the unchanged caption is rejected immediately by `PublisherRequestValidator.validate` at `PublisherRequestValidator.java:56-59`; a longer emoji caption is truncated to 2200 code points but is rejected by the same check afterward. The provider-bound 2200-character requirement therefore fails for precisely the Unicode input the new helper test covers.

Make the shared caption bound code-point based, or introduce an explicit provider-normalized validation path that does not reapply the UTF-16 limit. Add a service/controller test that submits a 2200-code-point emoji caption and verifies it reaches the claim/provider seam, plus an over-limit case that records the truncated fingerprint and payload.

### Provider-supplied Facebook upload URLs bypass the URL safety boundary

**Important/confirmed:** the Facebook start response is allowed to replace the configured rupload URL at `FacebookReelsClient.java:104-117`. That returned value is passed directly to `MetaClientSupport.postUpload`, which constructs `URI.create(url)` and sends the OAuth header at `MetaClientSupport.java:206-226`; it is not checked with `requireHttpsEndpoint`, `PublicMediaStorage.isSafeHttpsUrl`, a credential-query rejection, or an allowed-origin/path policy. A malformed or compromised response such as an HTTP URL, user-info URL, or URL containing `access_token` can therefore receive the page access token in the request header.

Validate the returned upload URL before any upload, requiring HTTPS, no userinfo/fragment, no credential-bearing query keys, and an approved Meta rupload origin/path while allowing only explicitly approved provider session/signature parameters. If validation fails after the remote start has created a video session, return an uncertain/reconciliation result without sending OAuth. Add HTTP, userinfo, credential-query, and valid signed-session URL tests.

### Explicit media hosting and bounded provider I/O

`PublicMediaStorage.isSafeHttpsUrl` rejects HTTP, userinfo, fragments, and unapproved query keys while allowing the documented signed-URL parameters. `ConfiguredPublicMediaStorage` only copies local files into an explicitly configured directory, tracks owned files, and cleans them in the Instagram client’s `finally` path; caller-provided HTTPS URLs are never deleted. `MetaPublisherApplication` supplies separate graph/upload request factories, and `MetaClientSupport` also bounds each operation with the configured request or upload deadline. The focused provider and application-context tests exercise these boundaries.

### Unrelated render-evidence admission changes in a Meta publisher patch

**Important/confirmed:** this delta modifies backend `ValidationEvidenceResponse`, `QualityReportSnapshots`, and `ValidationEvidenceService`, plus creative-render `ValidationEvidenceDto` and `ValidationEvidencePolicy` and their tests. The new path extracts `family8.renderAuthorization.status` and rejects every non-first-frame render whose value is not exactly `AUTHORIZED` (`ValidationEvidencePolicy.java:101-112`); legacy DTO constructors default the new field to `null`. This changes render admission behavior and is not part of the Task 3 Meta publisher contract.

Remove the backend and creative-render files from this Meta task. If the Family 8 authorization gate is independently required, split it into its own scoped change with its own compatibility and rollout evidence rather than coupling it to publisher migration and provider I/O.

### Test coverage and verification evidence

The focused Meta module passes 50/50 tests; the publisher-contract/support reactor passes 39/39, including the PostgreSQL repository tests; Spotless, package, and `git diff --check` pass. The changed render-service unit tests pass 41 focused tests, while its two PostgreSQL idempotency tests error on the pre-existing JSONB fixture binding; the full intelligence reactor also reports unrelated assertion/database fixture failures, so those broad failures do not establish a Meta regression. **Minor/confirmed:** the new tests prove helper-level emoji truncation but not service-level acceptance, and they omit the identity-mismatch, provider-returned upload URL, cleanup-on-failure, and executable migration scenarios described above. Add those regressions before treating the focused green suite as evidence for the complete Task 3 contract.

# RULESET 1.2 — Merging Genuine Gaps from ruleset-engine (Java) Design

**Date:** 2026-10-02
**Status:** Approved
**Target:** `content-intelligence-platform/intelligence/ml-service` (Python rule engine)
**Scope boundary:** This design touches only `intelligence/ml-service` (rule engine, data/rules YAML, docs). It does not modify `ruleset-engine/` (the Java project remains as-is, untouched, pending a separate decision about its disposition — this merge only extracts concepts, never code, from it). It does not touch `backend/`, `creative-render-service/`, `frontend/`, `lab/`, or `publisher/`.

## 1. Purpose

A gap analysis comparing `ruleset-engine/` (Java, Spring Boot, free-text + LLM concept validation) against `intelligence/ml-service`'s Python rule engine (structured Video-Plan-IR, deterministic + LLM-semantic validation) found that both systems independently solve the same problem — pre-render creative-concept quality gating — with significant overlap. Of Java's 19 documented rules, only 8 are seeded and only 3 have real (non-stub) code logic; the rest are either dead documentation or LLM-prompt-only with no deterministic backing. Most of Java's seeded rules are already duplicated, and improved upon, by existing Python rules (CONCEPT_001→HOOK_002, CONCEPT_003→CONCEPT_006, MOTION_001→MOTION_001).

The user's explicit decision: **do not port Java's implementations.** Java's keyword/regex matching on free text is architecturally inferior to Python's structured-IR approach and is largely dead/unexecuted code. Instead, extract the five genuine conceptual gaps Java identified (that Python's 21-rule set does not yet cover) and implement them natively in Python's structured-IR style, with Python becoming the single canonical pre-render quality engine. `ruleset-engine/` itself is left untouched by this work — its disposition (archive/delete/keep-as-reference) is a separate decision, not part of this design.

## 2. The Six New Rules Covering Five Identified Gaps

| Gap | New rule ID(s) | Family | Severity model |
|---|---|---|---|
| Single dominant mechanic | `CONCEPT_007` | concept_strength | BLOCKER on second independent mechanic |
| Story-detached gap | `BEAT_005` | visual_novelty (shares the "video stays on-topic" concern with BEAT_004) | CRITICAL when active problem is abandoned |
| Final peak intensity | `PAYOFF_004` | final_payoff | WARNING (optimization, not structural) |
| Fake-win escalation | `PAYOFF_005` | progression (companion to the existing `PAYOFF_002` fake-resolution-presence check) | WARNING, `NOT_APPLICABLE` when no fake-win beat exists |
| Dominant action ratio | `REPETITION_004` | visual_novelty (companion to `REPETITION_002`/`ATTEMPT_002`) | WARNING at >0.55, CRITICAL at >0.70 |
| Loopability | `PAYOFF_006` | final_payoff | INFO/bonus for strong loop, WARNING for a flagged weak ending (fade-out/"the end"/walks-away), PASS otherwise — never a hard blocker |

Six rule IDs because fake-win escalation and dominant-action-ratio are each a distinct, independently-testable check even though they're grouped under the same "gap" in the user's numbering (gap 4 is actually two separate checks sharing one schema dependency; gap 5 is one check). This matches the plan's instruction in §9 to write one golden test family per behavior, which only works cleanly with one rule ID per behavior.

## 3. Schema Changes (minimum necessary, confirmed against the current schema)

Checked `docs/VIDEO_PLAN_IR_SCHEMA.md` and `rule_engine.py` directly before deciding what's new. Two fields the user listed as "needed" **already exist and are already correctly placed** — no schema change required for them:

- **`beat.intensity: number` (1-10 scale) already exists** in the `Beat` interface and is already populated in the FAIL_001 example fixture. No new `intensityLevel` field is needed — the user's requested "common intensity concept" is this existing field, confirmed canonical by the user. `PAYOFF_004` and `PAYOFF_005` will read `beat.intensity` directly.
- **`finalPayoff.isPeakIntensity: boolean` already exists** in the schema but is **never read by any current evaluator** (confirmed: zero references to `isPeakIntensity` in `rule_engine.py`'s evaluator bodies). `PAYOFF_004` will be the first rule to actually use it — **but, per the user's explicit correction, only as a cross-check, never as a trusted input.** `PAYOFF_004` independently derives the peak from `beat.intensity` values and only consults `isPeakIntensity` to detect and surface a producer/evaluator disagreement (see §4) — an author writing `isPeakIntensity: true` must never, by itself, make the rule PASS.

Three new fields are genuinely needed and do not exist today. All three default-tolerant for backward compatibility — see §7a:

1. **`beats[].relatesToCoreProblem: boolean`** (optional; absent/missing is treated as `true` for pre-1.2 IRs — see §7a, not an error). Marks whether a beat advances/stays engaged with the established core mechanic/problem, as opposed to cutting away to story-irrelevant content (scenery, unrelated reaction shot, different prop). Used by `BEAT_005`. The user explicitly prefers this name over the originally-drafted `isStoryRelevant` ("fazla geniş ve yoruma açık") — `relatesToCoreProblem` ties the field directly to the one specific problem/mechanic the video is about, not a vaguer general "relevance" judgment.
2. **`coreMechanic.mechanicCount: integer`** (optional; absent/missing is treated as `1` for pre-1.2 IRs — see §7a). The number of independent physical/magical rules active in the concept. Per the user's explicit correction, this field is **not treated as ground truth to pass through** — see §4's revised `CONCEPT_007` semantics, which independently verifies the claim via a semantic evaluator rather than trusting the authored integer at face value. The field is retained (not dropped) because it still gives the semantic evaluator a stated claim to verify against, consistent with how `finalPayoff.isPeakIntensity` and `isRepeatOfOpening` are already treated as claims-to-verify elsewhere in this rule engine, not as facts.
3. **`finalPayoff.loopsToOpening: boolean`** and **`finalPayoff.loopQuality: "strong" | "weak" | "none"`** (both optional; absent/missing is treated as `loopsToOpening: false`, `loopQuality: "none"` for pre-1.2 IRs — see §7a). Mirrors the existing `isRepeatOfOpening` field's pattern (a sibling boolean on the same object) rather than introducing a new nested structure. Used by `PAYOFF_006`.

No change to `metadata`, `characters`, `setting`, `learningObjective`, `hook`, or `producibility` — none of the five gaps touch those sections.

## 4. Rule Semantics (detailed, addressing the user's specific worked examples)

### CONCEPT_007 — Single Dominant Mechanic

Per the user's explicit correction: `coreMechanic.mechanicCount` must not be treated as a trusted manual counter the rule simply reads and passes through — "bunu kullanıcı tarafından girilen güvenilir gerçek olarak kabul etmeyelim." The real distinction the rule must enforce is **same mechanic + multiple consequences** (one physical rule applied with escalating/varied results — always PASS) vs. **multiple independent mechanics** (a second, unrelated physical/magical rule introduced — FAIL). The authored `mechanicCount` integer is retained as a stated claim, verified rather than trusted:

```
authored_count = coreMechanic.mechanicCount  # author's claim

# Deterministic pre-check: if authored_count == 1, verify no beat's `consequence`
# describes a self-initiated behavior unrelated to the established physicalRule
# (e.g. an object acting with its own agency when the established rule is a
# passive cause-effect response to character action — a cheap heuristic
# red flag, not the final verdict).

# Semantic verification (LLM, via a new app.llm.semantic_checks function,
# e.g. count_independent_mechanics(core_mechanic_description, beat_descriptions)):
# ask whether the beats collectively exhibit one consistent physical/magical
# rule applied repeatedly (even with escalating/varied consequences) or
# whether a second, independent rule is introduced partway through — mirroring
# the existing check_twist_matches_rule / find_duplicate_strategy_pairs
# pattern already used by PAYOFF_003 / ATTEMPT_002 (semantic judgment only
# where deterministic evaluation is insufficient, per the user's own
# architecture principle in their original instructions).

derived_count = <verified mechanic count from the semantic check above>

if derived_count == 1:
    PASS, severity PASS
elif derived_count == 2:
    FAIL, severity CRITICAL  # a second independent mechanic, not yet "many"
else:  # >= 3
    FAIL, severity BLOCKER   # multiple unrelated rules, concept has lost focus

# If authored_count disagrees with derived_count, the rule's message surfaces
# the discrepancy explicitly (same "claim vs. verified" transparency pattern
# used by PAYOFF_004's isPeakIntensity cross-check) — the authored field never
# silently overrides the semantic verdict.
```

This directly encodes the user's puddle example: a puddle that goes from ankle-deep to knee-deep to waist-deep as the character tests it with toe/foot/both-feet is one mechanic (same rule, escalating consequences) — passes, regardless of how many distinct `consequence` strings describe the escalation. A puddle that does the above AND THEN starts chasing the character on its own is two independent mechanics — fails, because the second behavior (autonomous chasing) is not an escalation of "foot contact → depth increase," it's a new rule. `coreMechanic.mechanicCount` becomes effectively a cached/derived piece of metadata once the semantic check has run (per the user's "mechanicCount cached/derived metadata olabilir"), not an unchecked input. The `_evaluate_concept_007` method additionally cross-checks against `coreMechanic.consistency`: if `derived_count == 1` but `consistency == "breaking"`, that's a WARNING-level inconsistency flag (self-contradictory IR, worth surfacing even though it's not this rule's primary concern) — reuses the existing `CONSISTENCY_001` rule's field, no new field needed for it.

### BEAT_005 — Story Detached Gap

```
active_problem = at least one beat with isAttempt == true has occurred and
                  the final payoff has not yet started (i.e. we're "mid-story")
if active_problem:
    find max consecutive duration where relatesToCoreProblem == false
    if max_consecutive_detached_duration > 0.5s:
        FAIL, severity CRITICAL
    else:
        PASS
else:
    PASS (rule does not apply before the problem is established or after it's resolved)
```

The 0.5s tolerance is deliberately kept from Java's `maxDetachedDurationSec: 0.5` — the user explicitly said "0.5 sec civarı tolerans yalnızca transition için kabul edilebilir," i.e. keep the number, just don't keep the regex implementation. The 0.5s threshold itself is what keeps this rule from flagging ordinary short transitions/reaction beats as CRITICAL — per the user's explicit instruction, "bunun BLOCKER olması için yalnızca gerçekten narrative continuity'yi kıran durumları kullan; birkaç frame transition blocker olmamalı": a single `relatesToCoreProblem == false` beat under 0.5s (a brief transition cut, a quick reaction shot) never triggers this rule at all, since the check is on *consecutive detached duration*, not on the mere presence of any non-core-problem beat. Only a detached stretch that exceeds 0.5s — i.e. genuinely abandoning the active problem, not briefly cutting away — fails. This rule reads `beats[].relatesToCoreProblem` (new field, §3) and `beats[].isAttempt` (existing field) and `finalPayoff.startsAt` (existing field) — no other new data needed.

### PAYOFF_004 — Final Peak Intensity

```
max_prior_intensity = max(beat.intensity for beat in beats if beat.endTime <= finalPayoff.startsAt)
final_intensity = max(beat.intensity for beat in beats if beat.startTime >= finalPayoff.startsAt)

if final_intensity < max_prior_intensity:
    FAIL, severity WARNING   # optimization-level, not a blocker, per severity model in §5
elif final_intensity == max_prior_intensity:
    PASS, severity WARNING   # tied with the peak — acceptable but not ideal
else:
    PASS, severity PASS      # final payoff is strictly the most intense moment
```

Per the user's explicit instruction ("producer'ın isPeakIntensity=true yazması rule'u otomatik PASS ettirmesin"), this rule's PASS/FAIL verdict is **entirely derived from computed `beat.intensity` values** — `finalPayoff.isPeakIntensity` is never read as part of the pass/fail decision at all, only used afterward to detect and surface a producer/evaluator disagreement. If `finalPayoff.isPeakIntensity` disagrees with the computed result (author said `true` but computed `final_intensity < max_prior_intensity`, or vice versa), the rule's `message` surfaces that specific discrepancy as an additional note so a human/auto-fix pass can see the author's claim was wrong — but the discrepancy itself never changes the rule's outcome, which is always decided by the computed comparison alone. This is consistent with how `PAYOFF_001`/`PAYOFF_003` already treat payoff-related booleans as claims to be checked, not facts to pass through.

### PAYOFF_005 — Fake Win Escalation

```
fake_win_beats = [b for b in beats if b.consequenceType == "fake_win"]
if not fake_win_beats:
    outcome = NOT_APPLICABLE — "fake win not present; this check does not apply to this concept"
else:
    fake_win_beat = fake_win_beats[0]  # first fake-win beat, in timeline order
    intensity_before = fake_win_beat.intensity
    subsequent_beats = [b for b in beats if b.startTime > fake_win_beat.endTime]
    intensity_after = max((b.intensity for b in subsequent_beats), default=intensity_before)
    if intensity_after <= intensity_before:
        FAIL, severity WARNING
    else:
        PASS, severity PASS
```

Per the user's correction after this design's first draft: `RuleOutcome.UNKNOWN` must **not** be reused for this case. `UNKNOWN` means "this rule could not be evaluated" (e.g. `CONSISTENCY_002` before a video is rendered — the check is applicable but the evidence to run it doesn't exist yet). A fake-win-free concept is a different situation entirely: the check is **not applicable** to this concept at all, by design, not blocked on missing evidence. Collapsing these two into one outcome would corrupt downstream rule-coverage and rule-effectiveness measurement (e.g. "what % of evaluated concepts actually passed PAYOFF_005" needs to exclude not-applicable cases from the denominator for a different reason than it excludes could-not-evaluate cases, and a future analytics/learning layer measuring per-rule effectiveness must be able to tell these apart). This design therefore adds a new `RuleOutcome.NOT_APPLICABLE` enum value (see §6) rather than overloading `UNKNOWN`.

### REPETITION_004 — Dominant Action Ratio

```
attempts = [b for b in beats if b.isAttempt]
if len(attempts) == 0:
    PASS (nothing to measure)
verb_counts = count by normalized primaryVerb across attempts
dominant_ratio = max(verb_counts.values()) / len(attempts)

if dominant_ratio > 0.70:
    FAIL, severity CRITICAL
elif dominant_ratio > 0.55:
    FAIL, severity WARNING
else:
    PASS
```

Per the user's explicit correction to my original 1-to-1 Java port suggestion: Java's `0.55` is kept as the starting threshold but is **never** treated as a BLOCKER — "çünkü farklı consequence üreten aynı verb bazı konseptlerde geçerli olabilir." The two-tier WARNING/CRITICAL split (0.55 / 0.70) is the user's own refinement, not Java's. This rule is explicitly scoped as a companion to `ATTEMPT_002` (semantic duplicate-strategy check), not a replacement: `ATTEMPT_002` catches "verb-distinct but same-strategy" attempts (e.g. GRAB vs YANK judged semantically equivalent); `REPETITION_004` catches "one verb dominates numerically" even when every individual attempt is legitimately distinct in `ATTEMPT_002`'s judgment. The user's §5 instruction ("ATTEMPT_002 semantic duplicate check ile birlikte değerlendirilsin... sadece verb değiştirerek sistem kandırılamasın") is satisfied by these two rules running independently and both needing to pass — not by making one call the other.

### PAYOFF_006 — Loopability

```
if finalPayoff.loopsToOpening and finalPayoff.loopQuality == "strong":
    PASS, severity PASS, message notes this as a retention bonus
elif finalPayoff.loopsToOpening and finalPayoff.loopQuality == "weak":
    PASS, severity WARNING  # present but not strong — acceptable, not penalized
elif finalPayoff.isHardCut:  # existing field; a clean, ordinary hard cut with no
                              # loop claim is fully valid — neutral PASS, not a bonus
    PASS, severity PASS
else:
    # no loop, not a hard cut either — check for the specific weak-ending patterns
    # the user named: fade-out, "the end" caption, character walks away, long
    # held final pose (prolonged finished ending). These are read from a free-text
    # description already present on the final beat (finalPayoff has no dedicated
    # field for this, and none is being added — the rule inspects the last beat's
    # `consequence` or `action` string for this specific, narrow purpose only,
    # matching the existing precedent of PAYOFF_003 reading beat text for an LLM check)
    FAIL, severity WARNING  # never BLOCKER or CRITICAL, per the user's explicit
                             # instruction that a video must not be rejected
                             # solely for lacking a natural loop
```

Per §7 of the user's instructions (reaffirmed in their follow-up correction, §5 of this document), this rule's severity ceiling is WARNING — it can never block or critically fail a concept, only flag a missed optimization or an actively weak ending pattern. `loopQuality == "none"` on its own is never a FAIL condition — only the specific weak-ending patterns (fade-out/"the end"/walks-away/prolonged held pose) trigger the WARNING branch, and only when there's also no hard cut to fall back on as a valid neutral ending. The three outcomes the user named map directly: natural visual loop → bonus/strong PASS; ordinary hard cut → neutral PASS; prolonged/faded/walk-away ending → WARNING.

## 5. Severity Model (per the user's §7, applied consistently across all six new rules)

| Tier | Used by | Meaning |
|---|---|---|
| BLOCKER | `CONCEPT_007` (3+ mechanics) | Structural failure — concept must be rejected/regenerated, not patched |
| CRITICAL | `CONCEPT_007` (2 mechanics), `BEAT_005`, `REPETITION_004` (>0.70) | Structural failure, but a controlled patch is plausible rather than a full concept replacement |
| WARNING | `PAYOFF_004`, `PAYOFF_005`, `REPETITION_004` (>0.55-0.70), `PAYOFF_006` (weak ending) | Optimization-level — should fix, does not block render readiness on its own (consistent with the existing `is_render_ready` property's "zero blockers AND zero criticals" rule — a WARNING-only report can still be RENDER_READY) |
| PASS (bonus framing in message) | `PAYOFF_006` (strong loop) | Positive signal — same pattern as `CONCEPT_006`'s "5+ consequences" clean-PASS case |
| NOT_APPLICABLE | `PAYOFF_005` (no fake-win beat present) | The check does not apply to this concept by design — distinct from `UNKNOWN` (see §6) |

This mapping requires one new enum value — `RuleOutcome.NOT_APPLICABLE` (see §6) — but no new `Severity` values; `BLOCKER`/`CRITICAL`/`WARNING`/`PASS` all already exist in `app/quality/contracts.py`.

## 6. `RuleOutcome.NOT_APPLICABLE` — a Genuinely Distinct Outcome from `UNKNOWN`

Per the user's explicit correction, `UNKNOWN` and "not applicable" must not share one outcome value:

- **`UNKNOWN`** = the rule is applicable, but the evaluator cannot currently render a verdict because required evidence is missing (e.g. `CONSISTENCY_002` before a video exists — the rule *will* apply once rendering happens, it just can't run yet).
- **`NOT_APPLICABLE`** = the rule does not apply to this concept at all, by design (e.g. `PAYOFF_005` on a concept with no fake-win beat — there will never be evidence to evaluate, because the precondition for the check existing is itself absent).

Conflating these corrupts: family score denominators (both should currently be excluded, but for different reasons that matter once rule-coverage is tracked separately from rule-applicability), rule-coverage reporting ("how many of the 26 rules actually rendered a verdict on this concept" is a different question from "how many rules applied to this concept"), and — most importantly for the system's stated long-term direction — future rule-effectiveness learning, where "this rule never fires because it's rarely applicable" and "this rule never fires because evaluation keeps failing" are different problems requiring different fixes.

**Backward-compatibility check performed before adding this enum value:** searched every reference to `RuleOutcome` across `app/` (`rule_engine.py`, `quality_scorer.py`, `api/quality.py`, `validation/regression_checker.py`, `quality/contracts.py`, `llm/semantic_checks.py`) and confirmed there is no exhaustive `match`/if-elif-else chain anywhere that would silently misclassify a new enum member — every existing check is a positive `outcome is RuleOutcome.X` test (e.g. `is RuleOutcome.PASS`, `is RuleOutcome.FAIL`), never a catch-all `else` that assumes only four values exist. Adding a fifth `StrEnum` member is therefore safe without touching any of those call sites' existing logic; each one continues to correctly ignore `NOT_APPLICABLE` exactly as it already (accidentally, but correctly) ignores `UNKNOWN` today.

**Required code changes (both already registered as groundwork in §9, step 2):**

1. Add `NOT_APPLICABLE = "NOT_APPLICABLE"` to the `RuleOutcome` `StrEnum` in `app/quality/contracts.py`.
2. `RuleEngine._calculate_family_scores` currently only branches on `PASS`, `FAIL`, `SERVICE_ERROR` — `UNKNOWN` and `NOT_APPLICABLE` both fall through today with no explicit handling (confirmed: no `elif` for either). Add two explicit branches, both excluding the rule from the family's numerator and denominator (same net effect — "not counted" — but tracked as **separate counters** for observability, per the user's scoring table):
   - `elif rule.outcome is RuleOutcome.NOT_APPLICABLE:` → excluded from scoring; incremented in a new `not_applicable_count` tracked separately from scoring.
   - `elif rule.outcome is RuleOutcome.UNKNOWN:` → excluded from scoring; incremented in a new `unknown_count`, explicitly surfaced in `QualityReport` as "evaluation unavailable" (not silently merged with `not_applicable_count`), per the user's "UNKNOWN'ı ayrı takip et; default olarak denominator'dan çıkar ama observability'de 'evaluation unavailable' olarak görünür."
3. Add `not_applicable_rules` and `unknown_rules` (or equivalent derived accessor properties, following the existing `failed_rules`/`service_errors` pattern) to `QualityReport` in `app/quality/contracts.py`, so both are inspectable without re-deriving them from `evaluations` at every call site.

This is implemented as part of the schema/scoring groundwork task before any of the six new evaluators are written, per the user's requested order (schema → NOT_APPLICABLE semantics/scoring → evaluators → tests → ruleset version).

## 7a. Backward Compatibility (user's §7, mandatory)

RULESET 1.2 must not break validation of concepts authored against the 1.0/1.1 IR shape. All three new fields (§3) are **optional with explicit, documented defaults** rather than required fields, specifically so that a pre-1.2 IR missing them never produces a false FAIL:

| Field | Missing-field default | Rationale |
|---|---|---|
| `beats[].relatesToCoreProblem` | `true` | A pre-1.2 beat with no opinion on story-relevance is assumed on-topic; `BEAT_005` only ever fails on beats *explicitly* marked `false`, never on absence of the field. |
| `coreMechanic.mechanicCount` | `1` | A pre-1.2 concept with no stated mechanic count is assumed single-mechanic; `CONCEPT_007`'s semantic verification still runs (it doesn't depend on the authored field being present), so a genuinely multi-mechanic pre-1.2 concept can still be correctly flagged — the default only affects the *claim*, never the *verified* outcome. |
| `finalPayoff.loopsToOpening` / `loopQuality` | `false` / `"none"` | A pre-1.2 concept with no loop claim at all falls through `PAYOFF_006` to the hard-cut-or-weak-ending branch exactly as a 1.2 concept that explicitly declares no loop would — no special-casing needed beyond the default itself. |

This reverses an earlier draft of this design, which had marked these fields "required, never guessed" (mirroring the `isAttempt`/`primaryVerb` convention from the prior RULESET 1.1 effort). The user's explicit backward-compatibility requirement supersedes that convention for this specific set of fields — `isAttempt`/`primaryVerb` were introduced as part of a greenfield IR capability with no prior concepts to protect; these three fields must coexist with an existing corpus of 1.0/1.1-shaped concepts.

**Required before implementation, per the user's checklist:**
- `app/parser/prompt_parser.py` must supply the above defaults when the fields are absent from authored/parsed input (confirmed by inspection during the schema task, §9 step 1) — the parser must not require these fields, and must not fail or warn merely because they're absent.
- Schema/contract tests (§9 step 4) must include at least one fixture built from an existing 1.0/1.1-shaped IR (reusing the FAIL_001 Kiko fixture already in `VIDEO_PLAN_IR_SCHEMA.md`, unmodified) run through the 1.2 ruleset, asserting that `BEAT_005`, `CONCEPT_007`, and `PAYOFF_006` all evaluate without raising and without producing a false FAIL purely from the missing fields.
- `RULESET_1.1.yaml` is never modified (unchanged from the original design) — a caller still pinned to `ruleset_version="1.1"` is completely unaffected by any of this; the compatibility concern is specifically about running a *pre-1.2-shaped IR* through the *1.2 ruleset*, not about 1.1 itself changing.
- No database/API schema migration is required — the Video Plan IR is a plain JSON structure with no enforced schema at the storage layer (confirmed: `PromptVersionEntity.parsedIr` on the Java side, per the original architecture investigation, stores it as `jsonb` with no column-level shape constraints); "migration strategy" in this context means parser defaulting behavior only, not a database migration script.

## 8. Testing Requirements (per user's §9, applied per new rule)

Every one of the six new rules gets, at minimum:
- A PASS fixture
- A WARNING fixture (where the rule's severity model includes a WARNING tier)
- A CRITICAL/BLOCKER fixture (where applicable)
- A boundary-value test (e.g. `REPETITION_004` at exactly `0.55` and exactly `0.70`; `CONCEPT_007` at exactly `mechanicCount == 2`)
- A regression test confirming the existing 20-rule suite is unaffected by the new rules' registration

Golden/narrative tests requested explicitly by the user, mapped to the rule(s) each one exercises:

| Golden scenario | Exercises |
|---|---|
| Same mechanic + escalating consequences (the puddle depth example) → PASS | `CONCEPT_007` |
| Two unrelated physics rules in one concept → FAIL | `CONCEPT_007` |
| Distinct verbs but same strategy (GRAB vs YANK) → FAIL/WARN | `ATTEMPT_002` (existing rule — this scenario is already covered by current tests; included here only to confirm it still passes alongside the new `REPETITION_004`) |
| Same verb but meaningfully different consequence → must NOT false-positive | `REPETITION_004` (confirms the ratio check doesn't penalize legitimate same-verb-different-consequence patterns on its own — `ATTEMPT_002`'s semantic layer is what would catch an actual problem here, not this rule) |
| Fake win followed by weaker/repeated consequence → FAIL/WARN | `PAYOFF_005` |
| Final is biggest same-rule consequence → PASS | `PAYOFF_004` |
| Hard cut but no loop → acceptable | `PAYOFF_006` |

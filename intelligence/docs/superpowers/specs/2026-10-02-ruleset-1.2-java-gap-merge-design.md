# RULESET 1.2 — Merging Genuine Gaps from ruleset-engine (Java) Design

**Date:** 2026-10-02
**Status:** Approved
**Target:** `content-intelligence-platform/intelligence/ml-service` (Python rule engine)
**Scope boundary:** This design touches only `intelligence/ml-service` (rule engine, data/rules YAML, docs). It does not modify `ruleset-engine/` (the Java project remains as-is, untouched, pending a separate decision about its disposition — this merge only extracts concepts, never code, from it). It does not touch `backend/`, `creative-render-service/`, `frontend/`, `lab/`, or `publisher/`.

## 1. Purpose

A gap analysis comparing `ruleset-engine/` (Java, Spring Boot, free-text + LLM concept validation) against `intelligence/ml-service`'s Python rule engine (structured Video-Plan-IR, deterministic + LLM-semantic validation) found that both systems independently solve the same problem — pre-render creative-concept quality gating — with significant overlap. Of Java's 19 documented rules, only 8 are seeded and only 3 have real (non-stub) code logic; the rest are either dead documentation or LLM-prompt-only with no deterministic backing. Most of Java's seeded rules are already duplicated, and improved upon, by existing Python rules (CONCEPT_001→HOOK_002, CONCEPT_003→CONCEPT_006, MOTION_001→MOTION_001).

The user's explicit decision: **do not port Java's implementations.** Java's keyword/regex matching on free text is architecturally inferior to Python's structured-IR approach and is largely dead/unexecuted code. Instead, extract the five genuine conceptual gaps Java identified (that Python's 21-rule set does not yet cover) and implement them natively in Python's structured-IR style, with Python becoming the single canonical pre-render quality engine. `ruleset-engine/` itself is left untouched by this work — its disposition (archive/delete/keep-as-reference) is a separate decision, not part of this design.

## 2. The Five Gaps and Their Target Rules

| Gap | New rule ID(s) | Family | Severity model |
|---|---|---|---|
| Single dominant mechanic | `CONCEPT_007` | concept_strength | BLOCKER on second independent mechanic |
| Story-detached gap | `BEAT_005` | visual_novelty (shares the "video stays on-topic" concern with BEAT_004) | CRITICAL when active problem is abandoned |
| Final peak intensity | `PAYOFF_004` | final_payoff | WARNING (optimization, not structural) |
| Fake-win escalation | `PAYOFF_005` | progression (companion to the existing `PAYOFF_002` fake-resolution-presence check) | WARNING, `UNKNOWN`/not-applicable when no fake-win beat exists |
| Dominant action ratio | `REPETITION_004` | visual_novelty (companion to `REPETITION_002`/`ATTEMPT_002`) | WARNING at >0.55, CRITICAL at >0.70 |
| Loopability | `PAYOFF_006` | final_payoff | INFO/bonus for strong loop, WARNING for a flagged weak ending (fade-out/"the end"/walks-away), PASS otherwise — never a hard blocker |

Six rule IDs because fake-win escalation and dominant-action-ratio are each a distinct, independently-testable check even though they're grouped under the same "gap" in the user's numbering (gap 4 is actually two separate checks sharing one schema dependency; gap 5 is one check). This matches the plan's instruction in §9 to write one golden test family per behavior, which only works cleanly with one rule ID per behavior.

## 3. Schema Changes (minimum necessary, confirmed against the current schema)

Checked `docs/VIDEO_PLAN_IR_SCHEMA.md` and `rule_engine.py` directly before deciding what's new. Two fields the user listed as "needed" **already exist and are already correctly placed** — no schema change required for them:

- **`beat.intensity: number` (1-10 scale) already exists** in the `Beat` interface and is already populated in the FAIL_001 example fixture. No new `intensityLevel` field is needed — the user's requested "common intensity concept" is this existing field. `PAYOFF_004` and `PAYOFF_005` will read `beat.intensity` directly.
- **`finalPayoff.isPeakIntensity: boolean` already exists** in the schema but is **never read by any current evaluator** (confirmed: zero references to `isPeakIntensity` in `rule_engine.py`'s evaluator bodies). `PAYOFF_004` will be the first rule to actually use it, cross-checked against computed `max(beat.intensity for beat in beats)` rather than trusting the field blindly (see §4).

Three new fields are genuinely needed and do not exist today:

1. **`beats[].relatesToCoreProblem: boolean`** (required, defaults are never guessed — same "flag ambiguity, don't invent data" convention as `isAttempt`/`primaryVerb`). Marks whether a beat advances/stays engaged with the established core mechanic/problem, as opposed to cutting away to story-irrelevant content (scenery, unrelated reaction shot, different prop). Used by `BEAT_005`.
2. **`coreMechanic.mechanicCount: integer`** (required, minimum 1). The number of independent physical/magical rules active in the concept, as determined by the author/parser — **not** inferred by counting distinct `consequence` strings (same-mechanic beats can have many different consequences; this field exists precisely because consequence-counting cannot distinguish "same rule applied differently" from "second rule introduced," per the user's own puddle example). Used by `CONCEPT_007`.
3. **`finalPayoff.loopsToOpening: boolean`** and **`finalPayoff.loopQuality: "strong" | "weak" | "none"`** (both required, `loopQuality` defaults to `"none"` when `loopsToOpening` is `false`). Mirrors the existing `isRepeatOfOpening` field's pattern (a sibling boolean on the same object) rather than introducing a new nested structure. Used by `PAYOFF_006`.

No change to `metadata`, `characters`, `setting`, `learningObjective`, `hook`, or `producibility` — none of the five gaps touch those sections.

## 4. Rule Semantics (detailed, addressing the user's specific worked examples)

### CONCEPT_007 — Single Dominant Mechanic

```
if coreMechanic.mechanicCount == 1:
    PASS (severity PASS)
elif coreMechanic.mechanicCount == 2:
    FAIL, severity CRITICAL  # a second independent mechanic, not yet "many"
else:  # >= 3
    FAIL, severity BLOCKER   # multiple unrelated rules, concept has lost focus
```

This directly encodes the user's puddle example: a puddle that goes from ankle-deep to knee-deep to waist-deep as the character tests it with toe/foot/both-feet is `mechanicCount: 1` (same rule, escalating consequences) — passes. A puddle that does the above AND THEN starts chasing the character on its own is `mechanicCount: 2` — fails. The rule deliberately does **not** try to auto-derive mechanic count from `consequence` text diversity (that was explicitly rejected — "amaç sadece mechanicCount diye kullanıcıdan sayı istemek değil" was about not making it a dumb manual counter with no validation; the chosen design still takes an authored field, but the rule itself validates behavior around it rather than being a pass-through). The `_evaluate_concept_007` method will additionally cross-check against `coreMechanic.consistency`: if `mechanicCount == 1` but `consistency == "breaking"`, that's a WARNING-level inconsistency flag (the author claims one mechanic but also flagged the rule as breaking — likely a self-contradictory IR, worth surfacing even though it's not this rule's primary concern) — this cross-check reuses the existing `CONSISTENCY_001` rule's field, so no new field is needed for it.

### BEAT_005 — Story Detached Gap

```
active_problem = at least one beat with isAttempt == true has occurred and
                  the final payoff has not yet started (i.e. we're "mid-story")
if active_problem:
    find max consecutive duration where relatesToCoreProblem == false
    if max_consecutive_detached_duration > 0.5s:
        FAIL, severity CRITICAL
    else:
        PASS
else:
    PASS (rule does not apply before the problem is established or after it's resolved)
```

The 0.5s tolerance is deliberately kept from Java's `maxDetachedDurationSec: 0.5` — the user explicitly said "0.5 sec civarı tolerans yalnızca transition için kabul edilebilir," i.e. keep the number, just don't keep the regex implementation. This rule reads `beats[].relatesToCoreProblem` (new field, §3) and `beats[].isAttempt` (existing field) and `finalPayoff.startsAt` (existing field) — no other new data needed.

### PAYOFF_004 — Final Peak Intensity

```
max_prior_intensity = max(beat.intensity for beat in beats if beat.endTime <= finalPayoff.startsAt)
final_intensity = max(beat.intensity for beat in beats if beat.startTime >= finalPayoff.startsAt)

if final_intensity < max_prior_intensity:
    FAIL, severity WARNING   # optimization-level, not a blocker, per severity model in §5
elif final_intensity == max_prior_intensity:
    PASS, severity WARNING   # tied with the peak — acceptable but not ideal
else:
    PASS, severity PASS      # final payoff is strictly the most intense moment
```

This independently computes the peak from `beat.intensity` rather than trusting `finalPayoff.isPeakIntensity` as an unverified author claim — consistent with how `PAYOFF_001`/`PAYOFF_003` already treat payoff-related booleans as claims to be checked, not facts to pass through. If `finalPayoff.isPeakIntensity` disagrees with the computed result (author said `true` but computed `final_intensity < max_prior_intensity`), the rule's `message` surfaces that specific discrepancy so a human/auto-fix pass can see the author's claim was wrong, rather than silently overriding it.

### PAYOFF_005 — Fake Win Escalation

```
fake_win_beats = [b for b in beats if b.consequenceType == "fake_win"]
if not fake_win_beats:
    outcome = UNKNOWN (not FAIL, not PASS) — "fake win not present; rule not applicable"
else:
    fake_win_beat = fake_win_beats[0]  # first fake-win beat, in timeline order
    intensity_before = fake_win_beat.intensity
    subsequent_beats = [b for b in beats if b.startTime > fake_win_beat.endTime]
    intensity_after = max((b.intensity for b in subsequent_beats), default=intensity_before)
    if intensity_after <= intensity_before:
        FAIL, severity WARNING
    else:
        PASS, severity PASS
```

Per the user's explicit instruction: "Fake win yoksa rule NOT_APPLICABLE olabilir; fake win'i her videoya zorunlu yapma." `RuleOutcome.UNKNOWN` (already defined in `app/quality/contracts.py`, already used by `CONSISTENCY_002` for its own "not applicable yet" case) is reused for this rather than inventing a new `NOT_APPLICABLE` enum value — same semantic ("this rule could not render a verdict"), same existing type, no contract change needed. `_calculate_family_scores` already handles `SERVICE_ERROR` outcomes by contributing a zero; `UNKNOWN` outcomes need the same explicit handling added (see §6) so a `PAYOFF_005: UNKNOWN` doesn't silently drop out of the family average or get miscounted as a pass.

### REPETITION_004 — Dominant Action Ratio

```
attempts = [b for b in beats if b.isAttempt]
if len(attempts) == 0:
    PASS (nothing to measure)
verb_counts = count by normalized primaryVerb across attempts
dominant_ratio = max(verb_counts.values()) / len(attempts)

if dominant_ratio > 0.70:
    FAIL, severity CRITICAL
elif dominant_ratio > 0.55:
    FAIL, severity WARNING
else:
    PASS
```

Per the user's explicit correction to my original 1-to-1 Java port suggestion: Java's `0.55` is kept as the starting threshold but is **never** treated as a BLOCKER — "çünkü farklı consequence üreten aynı verb bazı konseptlerde geçerli olabilir." The two-tier WARNING/CRITICAL split (0.55 / 0.70) is the user's own refinement, not Java's. This rule is explicitly scoped as a companion to `ATTEMPT_002` (semantic duplicate-strategy check), not a replacement: `ATTEMPT_002` catches "verb-distinct but same-strategy" attempts (e.g. GRAB vs YANK judged semantically equivalent); `REPETITION_004` catches "one verb dominates numerically" even when every individual attempt is legitimately distinct in `ATTEMPT_002`'s judgment. The user's §5 instruction ("ATTEMPT_002 semantic duplicate check ile birlikte değerlendirilsin... sadece verb değiştirerek sistem kandırılamasın") is satisfied by these two rules running independently and both needing to pass — not by making one call the other.

### PAYOFF_006 — Loopability

```
if finalPayoff.loopsToOpening and finalPayoff.loopQuality == "strong":
    PASS, severity PASS, message notes this as a retention bonus
elif finalPayoff.loopsToOpening and finalPayoff.loopQuality == "weak":
    PASS, severity WARNING  # present but not strong — acceptable, not penalized
elif finalPayoff.isHardCut:  # existing field; a clean hard cut with no loop claim is fine
    PASS, severity PASS
else:
    # no loop, not a hard cut either — check for the specific weak-ending patterns
    # the user named: fade-out, "the end" caption, character walks away, long
    # held final pose. These are read from a free-text description already
    # present on the final beat (finalPayoff has no dedicated field for this,
    # and none is being added — the rule inspects the last beat's `consequence`
    # or `action` string for this specific, narrow purpose only, matching the
    # existing precedent of PAYOFF_003 reading beat text for an LLM check)
    FAIL, severity WARNING  # never BLOCKER or CRITICAL, per the user's explicit
                             # instruction that a video must not be rejected
                             # solely for lacking a natural loop
```

Per §7 of the user's instructions, this rule's severity ceiling is WARNING — it can never block or critically fail a concept, only flag a missed optimization or an actively weak ending pattern. The "strong loop" case is explicitly framed as a bonus (contributing a clean PASS/PASS, same positive signal `CONCEPT_006`'s 5+-consequence case already uses), not merely tolerated.

## 5. Severity Model (per the user's §7, applied consistently across all six new rules)

| Tier | Used by | Meaning |
|---|---|---|
| BLOCKER | `CONCEPT_007` (3+ mechanics) | Structural failure — concept must be rejected/regenerated, not patched |
| CRITICAL | `CONCEPT_007` (2 mechanics), `BEAT_005`, `REPETITION_004` (>0.70) | Structural failure, but a controlled patch is plausible rather than a full concept replacement |
| WARNING | `PAYOFF_004`, `PAYOFF_005`, `REPETITION_004` (>0.55-0.70), `PAYOFF_006` (weak ending) | Optimization-level — should fix, does not block render readiness on its own (consistent with the existing `is_render_ready` property's "zero blockers AND zero criticals" rule — a WARNING-only report can still be RENDER_READY) |
| PASS (bonus framing in message) | `PAYOFF_006` (strong loop) | Positive signal — same pattern as `CONCEPT_006`'s "5+ consequences" clean-PASS case |
| UNKNOWN | `PAYOFF_005` (no fake-win beat present) | Not applicable — rule could not render a verdict, must not be miscounted as a pass or silently dropped |

This mapping directly implements the user's instruction and requires no new `Severity` or `RuleOutcome` enum values — `BLOCKER`/`CRITICAL`/`WARNING`/`PASS` and `UNKNOWN` all already exist in `app/quality/contracts.py`.

## 6. Scoring/Aggregation Fix Required for UNKNOWN

`RuleEngine._calculate_family_scores` (current code) only branches on `RuleOutcome.PASS`, `RuleOutcome.FAIL`, and `RuleOutcome.SERVICE_ERROR` — there is currently no rule in the entire 21-rule set that can return `UNKNOWN` from a normal (non-service-error) evaluation path, so this branch has never been needed. `PAYOFF_005` introduces the first legitimate `UNKNOWN` outcome from normal evaluation logic (not a failure condition — "fake win absent" is an expected, valid state for many concepts). The fix: add an explicit `elif rule.outcome is RuleOutcome.UNKNOWN` branch that **excludes the rule from both the numerator and denominator** of its family's average (neither contributes points nor counts against `count`), so a `PAYOFF_005: UNKNOWN` on a concept with no fake-win beat has precisely zero effect on the `progression` family's score — not a pass, not a fail, not present. This is a one-line-equivalent change to existing, already-reviewed code (not new business logic, just closing a branch gap that six new rules now make reachable) and will be implemented as part of the schema/scoring groundwork task before any new evaluator is written, per the user's requested order (schema → evaluators → tests → ruleset version).

## 7. RULESET_1.1 Metadata Cleanup (user's §1, "clean up existing inconsistencies first")

Confirmed via direct inspection of `rule_engine.py`'s `self.evaluators` registry (quoted in full in §3's code excerpt above): there are exactly 20 registered rule IDs — the 10 original RULESET_1.0 rules (`CONCEPT_006`, `BEAT_004`, `REPETITION_002`, `REPETITION_003`, `NOVELTY_001`, `PROGRESSION_005`, `ESCALATION_004`, `PAYOFF_001`, `PRODUCIBILITY_001`, `CONSISTENCY_001`) plus the 10 added in RULESET_1.1 (`HOOK_002`, `HOOK_003`, `MOTION_001`, `ATTEMPT_001`, `CHAR_002`, `PRODUCIBILITY_002`, `PAYOFF_002`, `ATTEMPT_002`, `PAYOFF_003`, `CONSISTENCY_002`). `RULESET_1.1.yaml`'s `ruleset_summary.total_rules: 20` (fixed in the prior RULESET 1.1 effort's Task 13 to recompute from the actual list rather than carry a stale copy) is therefore correct. An earlier gap-analysis pass by a different sub-agent in this session reported a 21-entry count for the same ruleset; that count does not match this direct registry read and is treated as that sub-agent's error, not a real discrepancy — no action needed.

The `MOTION_001` ID-collision concern (same rule ID string used by both Java and Python for related-but-differently-scoped checks) is a cross-project naming collision, not an internal Python inconsistency — since Java's `MOTION_001` is never ported (per this design's core decision), there is nothing to reconcile on the Python side. No action needed; noting it here only so the next person reviewing this doc understands why §1's "reconcile the MOTION_001 collision" instruction resulted in "no code change" rather than being silently dropped.

The Java "22 rules" stale-metadata claim is Java's own documentation problem, inside a project this design explicitly does not modify — not actionable here.

## 8. Testing Requirements (per user's §9, applied per new rule)

Every one of the six new rules gets, at minimum:
- A PASS fixture
- A WARNING fixture (where the rule's severity model includes a WARNING tier)
- A CRITICAL/BLOCKER fixture (where applicable)
- A boundary-value test (e.g. `REPETITION_004` at exactly `0.55` and exactly `0.70`; `CONCEPT_007` at exactly `mechanicCount == 2`)
- A regression test confirming the existing 20-rule suite is unaffected by the new rules' registration

Golden/narrative tests requested explicitly by the user, mapped to the rule(s) each one exercises:

| Golden scenario | Exercises |
|---|---|
| Same mechanic + escalating consequences (the puddle depth example) → PASS | `CONCEPT_007` |
| Two unrelated physics rules in one concept → FAIL | `CONCEPT_007` |
| Distinct verbs but same strategy (GRAB vs YANK) → FAIL/WARN | `ATTEMPT_002` (existing rule — this scenario is already covered by current tests; included here only to confirm it still passes alongside the new `REPETITION_004`) |
| Same verb but meaningfully different consequence → must NOT false-positive | `REPETITION_004` (confirms the ratio check doesn't penalize legitimate same-verb-different-consequence patterns on its own — `ATTEMPT_002`'s semantic layer is what would catch an actual problem here, not this rule) |
| Fake win followed by weaker/repeated consequence → FAIL/WARN | `PAYOFF_005` |
| Final is biggest same-rule consequence → PASS | `PAYOFF_004` |
| Hard cut but no loop → acceptable | `PAYOFF_006` |
| Natural loop → strong pass/bonus | `PAYOFF_006` |

## 9. Implementation Order (per user's explicit requirement)

1. **Schema** — add the three new IR fields (§3) to `VIDEO_PLAN_IR_SCHEMA.md`, bump schema version to 1.2, update the parser if it needs to read/pass through the new fields (check `prompt_parser.py` for whether it needs explicit handling or whether these are purely author-set fields with no parser involvement, same as `isAttempt`/`primaryVerb` in the prior round).
2. **Scoring groundwork** — the one `UNKNOWN`-handling branch fix in `_calculate_family_scores` (§6), landed and tested independently before any of the six new evaluators are added, so it's reviewable in isolation.
3. **Evaluators** — six new `_evaluate_*` methods + registry entries in `rule_engine.py`, implementing §4's semantics.
4. **Tests** — per §8, including the golden scenarios.
5. **Ruleset version** — generate `RULESET_1.2.yaml` via the existing `RuleVersionManager.create_new_version()` machinery (already fixed and exercised in the prior RULESET 1.1 effort), adding the six new rule entries. `RULESET_1.1.yaml` is never modified, matching the established pattern of each version being independently loadable.

This design intentionally stops short of producing the full task-by-task implementation plan — per the user's own closing instruction ("implementasyona başlamadan önce mevcut şemayı kontrol et... sonra kısa bir schema-change planı çıkar; ardından RULESET 1.2 implementasyonuna geç"), this document **is** that schema-change plan. The next step is a `writing-plans`-style implementation plan covering steps 1-5 above as discrete, TDD-structured tasks, to be produced after this design is confirmed.
